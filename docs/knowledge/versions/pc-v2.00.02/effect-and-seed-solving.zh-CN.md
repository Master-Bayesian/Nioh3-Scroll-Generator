# 词条、恩宠与 Seed 求解 — PC v2.00.02

## 玩家版结论

“能逆向”不等于“所有条件都各自算出一张 Seed 表再做集合交集”。当前实现把约束分成两类：

| 条件 | 当前方法 | 能否直接数学求逆 | 最终门禁 |
| --- | --- | --- | --- |
| 一、二周目主词条 | 对应上下文的固定 draw 映射 | 可以 | 原生/离线完整生成复核 |
| 三周目稀有度 3/4 主词条 | GPU 批量预筛 | 不能单独当作固定 draw | 完整词条生成器精确回放 |
| 稀有度 4 恩宠 | stage-one 的 first-draw 区间可逆 | 只能逆出完成前候选 | R4 finalizer 精确回放，确认最终是否保留 |
| 普通副词条 | 类别、冲突、配额、权重、重试共同决定；R4 的 1–2 组条件在 GPU 内运行补全器，3 组以上使用无漏解 `N−1` 前筛 | 不能可靠独立求逆 | GPU 筛选后，再由完整词条生成器逐 Seed 精确回放 |
| 词条数值/百分位 | 依赖最终命中的槽位与数值 roll | 不能独立求逆 | 完整词条生成器精确回放 |
| 地形影响 | 当前按完整辅助生成器重放 | 暂未认证为独立固定 draw | 完整辅助生成器精确回放 |
| 出现敌人 | 依赖 Class、role、周目、地形、预算、联动组和动态候选池 | 不能可靠直接求逆 | 结构预检后完整辅助生成器精确回放 |
| 特殊规则及数值变体 | 依赖有序生成、门槛、重试和变化中的候选池 | 不能可靠直接求逆 | 完整辅助生成器精确回放 |

数学可逆部分用于快速缩小候选域；路径相关部分不是“忽略”，而是对缩小后的 Seed 做精确正向生成。没有固定 draw 条件时，程序按可恢复游标分块覆盖完整自然 Seed 域，不把任意前一百万个 Seed 当作全部空间。

稀有度 4 只指定一到两个独立条件组时，DirectCompute 路径会生成四个第一阶段普通词条及其百分位、临时恩宠，并在 GPU 内运行完整补全器，然后才按最终五个槽判断玩家条件。主词条位置、“任意普通槽”、必含项和 OR 组语义都会保留；不再因为 `N−1` 选择性不足而停止。

三个以上独立条件组继续使用更便宜但同样无漏解的必要条件：补全器最多改写一个物理槽，因此第一阶段至少必须命中合并后的 `N−1` 组。GPU 先做该前筛，最终接受仍由精确回放决定。

这仍然不是每个词条各自拥有一个闭式逆函数。所有 GPU 幸存 Seed 还会由认证的 CPU 生成器独立完整回放后才显示或写入。当前保留的本地对照中，分散的 2,048 个 Seed 双条件掩码和连续的 1,024 个 Seed 单条件掩码均为 0 差异，并另外检查了等级 1 的 `value == 1` 门槛和主词条位置语义；这些检查不替代既有的原生阶段／最终记录 parity 证据。

## “必含”与“任一组”

- 多个“必含”条件是 AND：每一项都必须出现在同一张最终绘卷中。
- 同一个“任一组”中的多个选项是 OR：最终出现其中任意一项即可。
- 不同“任一组”之间仍然是 AND。例如“任一组 1”为 A/B/C，“任一组 2”为 X/Y，最终必须命中 A/B/C 中至少一项，并命中 X/Y 中至少一项。
- 主词条候选本身就是 OR：把主词条候选数设为 3，表示前三项任一成为主词条即可。
- 任一组中的副词条目前按“任意数值”匹配；若必须限制具体百分位，请把该词条改回“必含”再选择数值门槛。

## 为什么不能把副词条、敌人和规则都写成闭式方程

已恢复的 LCG 为：

```text
state = state * 0x10DCD + 1 mod 2^32
output = state >> 16
```

固定第 N 次 draw 的输出区间可以利用模逆元求出有限前像。但副词条、敌人和特殊规则在生成途中会因冲突、配额、门槛、拒绝采样和重试消耗不定数量的 RNG draw。同一目标不再对应一个固定的“第 N 次 draw 区间”，强行套用固定方程会漏解或报出假解。

因此当前正确流程是：

1. 先用槽位、冲突组、敌人 Class/role 和周目规则排除结构无解组合。
2. 有已认证固定 draw 条件时，用数学逆向构造 Seed 候选族。
3. 其余条件交给完整离线生成器精确回放。
4. 每找到一张完整匹配绘卷就立即显示，同时保存不重复的继续游标。

## 稀有度 4 与 `0xBABD`

稀有度 4 先生成 stage-one 记录，再运行完成器。stage-one 第 5 槽的恩宠候选不保证出现在最终记录中。最终记录中的 `0xBABD` 是“月读的恩宠”；但 Seed `183696634` 的 stage-one 候选经过 finalizer 后会成为 `0xAE5A`“技之深奥”。这不是固定的 ID 替换表，而是完整完成器重新生成合法结果。

因此软件必须用“游戏版本 + 绘卷类型 + 稀有度 + 生成阶段 + 槽位角色/序号 + raw ID + 完整槽位字段”解析语义，不能只维护一张全局 `raw ID → 名称` 表。
