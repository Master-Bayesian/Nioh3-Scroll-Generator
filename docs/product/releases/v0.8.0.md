# v0.8.0 engineering record

Status: **in development; published v0.7.5 baseline integrated, M0/M1 numerical slices verified locally, no product cutover, package, tag, or publication**

Created: 2026-09-15

This record owns the v0.8.0 release-line scope and its evidence boundary. It is
not a release note: no v0.8.0 application package, tag, signed feed, installer,
or public release exists. Local domain verification is not shipped behavior.
The published baseline is [v0.7.5](v0.7.5.md) (product commit
`533694ebad21906aecbb6ab5283e04e760ce6c09`, owner-confirmed search-continuation
and icon fixes), integrated into this branch by merge `263f46d`; the earlier
[v0.7.4](v0.7.4.md) baseline is historical. The current product position is in
[the current handoff](../../knowledge/CURRENT_HANDOFF.md), and the migration
baseline, architecture, and stage sequence are in
[the Rust backend migration record](../../knowledge/V080_RUST_BACKEND_MIGRATION.md).

## Position

An Astra-led incremental Rust backend migration is active under the project
owner's direction. The first slices are standalone domain/data libraries with an
offline cross-language parity gate; M1 enemy-generation parity is verified locally.
The shipped React/WebView2 product and its
one-file delivery contract are preserved while backend components are replaced
incrementally, and the production backend has not switched.

M2.1 adds the ordinary NG3 effect-sequence path to those offline libraries:
effect tables, scroll records and the sequence core, parity-gated against the
retained Python reference through the production data adapter (549 emitted rows
with zero differences, including a 216-row cross-level sweep that exercises the
curve clamp, three native byte anchors, and a permanent adapter content-parity
guard). M2.2 adds R4 completion finalization and the paired stage-one/install and
finalized/preview records, byte-exact against all ten tracked 232-byte native
pairs through the same production adapter, with a measured reveal-branch
comparison and a corrected effect-area level-sensitivity measurement. M2.3a adds
a development-only Rust read-only worker that serves the preview subset over the
shipped framed-JSON protocol, matching the Python worker on a 189-preview
subprocess matrix and passing runtime independence checks (it answers with
Python absent from `PATH`, fails closed on an empty data root, and rebuilds from
the current candidate). All three are local offline evidence only.
`GenerationContext` digest binding over the wire, candidate identity beyond the
preview payload, search orchestration, product wiring and packaging remain
unimplemented, and the native corpus exercises only `reveal = true` at level 180.

M2.3b1 serves a bounded search surface inside the development worker and its
acceptance is green: the preview gate derives the contract's method set from
`request.schema.json`, validates every frame against `response.schema.json` and
compares the whole `capabilities` object against live probes, and the search gate
covers the canonical v0.7.5 three-rule regression in one continuing job with its
bounded control, effect/enemy page identity/order/cursor parity, auxiliary-only
pages at rarity 3 and 5, responsive cancel and resume, resume-token rejection
(forged, changed query, context, policy, continuation and cross-process),
candidate ownership and export, accelerator absence, and the unported NG4/NG5
boundary. Measured on the frozen tree: `tests/migration` 78 passed / 0 failed,
`cargo test` worker 66 library + 3 binary / domain 71 / data 17, all zero
failures. The served routes are the fused auxiliary pivot and the rarity-4
primary pivot; effect-preimage searches, rarity-3 primary search,
secondary/roll-only replay, Grace-filtered pivots, terrain option ids and
playthrough 4/5 are refused with a reason naming the missing route, and the
DirectCompute effect filter and NG4/NG5 cache are not advertised. No product
cutover, package, tag or publication is implied, and nothing is wired into the
shipped host.

### Current position (M2.3d / M3 / M4, 2026-09-15)

The two paragraphs above record M2.3a and M2.3b1. Their "remain unimplemented"
list and their "refused / not advertised" list are superseded by what follows;
they stay as history rather than being edited.

- **Read-only worker.** The whole read-only surface is served, including the
  DirectCompute effect-filter capability and `cached_rarity5_playthroughs:
  [4, 5]`. The M2.3d gates are green;
  [`V080_RUST_BACKEND_MIGRATION.md`](../../knowledge/V080_RUST_BACKEND_MIGRATION.md)
  and the M2.3d handoff hold the numbers.
- **Protected host** (`crates/nioh3-protected`, new). Serves the runtime role -
  ownership, temporary overrides, reviewed live add and batch, and the
  `generate` / `search` / `capture_grace` scan and measured-map loops - and the
  save role. Current boundary statement:
  [`RUNTIME_HANDOFF.md`](../../../deliverables/m3-protected-host/RUNTIME_HANDOFF.md);
  functional evidence in
  [`EVIDENCE_RUNTIME_HOST.md`](../../../deliverables/m3-protected-host/EVIDENCE_RUNTIME_HOST.md)
  and matched-workload performance in
  [`perf/scan_perf.json`](../../../deliverables/m3-protected-host/perf/scan_perf.json).
- **Packaged profile (M4 opt-in): implemented.** The packaged host selects the
  Rust worker graph from the staged `worker/worker-backend.json` inside the
  package, validates schema/backend/roles/binary names/roots/package
  confinement/per-binary sha256, substitutes the `<runtime>` placeholder, and
  refuses a missing, malformed, escaping or under-declared manifest by name
  instead of falling back. `tools/package_tauri.py` now stages that manifest into
  the package, which it previously did not. Acceptance compares the resolved
  argv against the staged manifest for all three roles and confirmed
  `backend=rust-packaged` with the staged binary hash.
- **Default backend switch (owner-authorized, local only).** The packaged
  product now defaults to the staged Rust worker graph: `tools/build_tauri.ps1`,
  `tools/package_tauri.py` and the `release.yml` dispatch input all default to
  `rust`, the one-file acceptance asserts the staged worker identity from inside
  the product, and CI carries the packaging job as a required gate. The
  PyInstaller worker is retained for development, parity and the legacy Tk path
  and is no longer shipped. This authorization covers a local
  backend-validation build only: no push, workflow dispatch, tag, update feed or
  publication, and no real game or user-save write.
- **Version identity is deliberately unchanged.** This internal build keeps the
  existing product version, so its bytes are not the published v0.7.5 stable
  release and must never be represented as the stable download.
- **Frontend acceptance is development-build (dirty) evidence only** - debug host
  against a staged runtime, isolated state and synthetic encrypted fixture, no
  release/one-file build, no real game process, no user save. Accepted on the
  rust-packaged graph: handshake, catalog in zh-CN/en-US/ja-JP
  (50/21/6/487/277/103), preview, the v0.7.5 regression (seed `226061463` at
  cursor `158614759`), cancel+resume continuation, favorites persistence across a
  host restart, settings, and diagnostics reporting the staged binary hash. The
  cart/R4 plan/commit and editor/delete/backup-restore legs were blocked on the
  Rust save host refusing `effect_sequence_only` candidates at `install_record`
  while its own `install_blocker` permitted them (owner
  `/root/m3_save_acceptance`).
  `deliverables/v080-completion-readiness/PACKAGED_FRONTEND_STATUS.md` now records
  both former blockers fixed and every named leg green on the rust-packaged
  graph; that is lane evidence from a development-shape run and is not a
  same-candidate packaged acceptance.
- **Open blockers.** The four live flows listed in `RUNTIME_HANDOFF.md` and the
  same-candidate packaged UI acceptance. Live acceptance has not run - no game
  process, save, debugger or Cheat Engine session has been touched.

## Scope carried over from v0.7.4

The [v0.7.4 record](v0.7.4.md) defers equipment and Soul Core generation/editing
to this product line because they introduce new generation, data, and write
contracts. Its two separate concepts are the legal equipment generator and the
noncanonical affix editor, each with its own evidence and safety boundary.
Equipment generation and editing are not promised by this migration and require
separate research.

Those areas are not covered by the shipped scroll search, live-add, or
protected-save contracts, and this record does not relax the frozen operation
policy that blocks generated NG4/NG5 installs.

## Evidence boundary

M0 and M1 passed local Rust unit tests and release-mode cross-language
comparison. Exact scope, commands and results are recorded in
[M0 verification](../../knowledge/V080_RUST_BACKEND_MIGRATION.md#verification).
The existing Python product implementation remains active and unchanged.

Every anchor above is offline, static, or synthetic evidence. None of it
establishes live-game behavior, save mutation, persistence, or packaged user
acceptance. A Rust boundary must satisfy the same gates before any v0.8.0
release claim, and the shipped v0.7.5 behavior remains the baseline to preserve.

## Implementation and release decisions

- The first slice adds Rust domain tests and cross-language parity to push/PR
  CI. Existing desktop tests already run in `frontend-v2.yml`; host/launcher
  Rust tests remain release gates until their next affected slice.
- Whether the C++/CUDA numerical helpers are ported, kept, or replaced, which
  needs its own parity and performance decision rather than language uniformity.
- The first product cutover targets read-only generation and preview after
  exact output and worker lifecycle parity. The primary agent defines each
  bounded assignment; later write-path acceptance follows its operation risks.
- The v0.8.0 version bump, tag, release notes, and publication window.
